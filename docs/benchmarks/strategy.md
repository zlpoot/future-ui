## 三层正确性

结构正确：契约/Schema/组件结构可校验。
交互正确：键盘、状态、事件、局部修改与视觉/可访问行为符合定义。
业务正确：输入、权限、实际 effect、结果和界面投影一致。

结构通过不能代替交互或业务通过；请求已发送不等于业务完成；取消/超时不等于回滚。

## AI 对照设计

基线组：直接使用所冻结版本的 Ark UI 及该环境可用的官方开发文档/工具。
实验组：相同底层组件与任务，加入 future-ui 契约、结构化目录、校验和局部修改工具。

控制模型/版本、推理和调用预算、初始上下文、依赖版本、环境、任务说明与允许工具权限。两组按任务配对，避免把更大 token 预算或额外人工帮助误当成框架收益。适用时随机化组顺序并避免跨组泄露答案。

候选任务族：创建合法表单、修复无效组合、修改指定区域不伤及其他区域、更换主题、处理异步错误、根据诊断修复可访问性问题、接入共享业务动作。任务清单/样本量/重试上限/成功判据必须在试验前冻结；当前均未执行。

记录首轮通过率、完成率、修复轮数、最终交互正确率、改动引发的回归、token/成本/时延和失败类别。区分编译通过与最终功能正确；保留所有尝试、普通失败和未完成样本。结果按任务集和样本量限定解释，不根据少量样本泛称 AI 更强。

收费模型、provider 和凭据需要明确授权；未获授权只可做设计，不能造出“0 成本实测”或模型替身冒充真实实验。

## 证据等级与报告

准备文档自查、确定性模拟测试、真实浏览器集成、真实模型调用、真实外部业务写分别记账。第一版默认受控本地 fixture，不做真实购物/付款。模拟允许用于单测，但不得提升为 live 支持结论。

每次报告列 exact head、环境/版本、命令、结果、原始产物位置、未运行项及原因。阶段最终结论基于同一代码基线；失败、未测、延期和排除项分别列出。

## Calibration 与 Acceptance 分离

允许在正式验收前做一次明确标记的 calibration/pilot，用于获得 bundle、初始化时延、任务难度或模型成功率的基线并制定合理门槛。**用于制定门槛的数据不得同时计入最终 Acceptance**；calibration 结束后先冻结测量方法、样本/任务集、阈值和停止条件，再运行独立 acceptance 样本。若修改关键方法或阈值，需要重新说明并重启受影响的 acceptance，而不是回填旧结果。

AI 对照同样遵守此规则：用于调任务、提示或成功判据的 pilot 样本不进入最终效果统计，避免根据已看到的结果调门槛。

## 门槛与比例

普通任务使用最小充分检查，保留影响消费者；不要求每个文档 PR 搭一套 CI。调用权限/unknown write 的最终行为与阶段验收做独立 Verify。高风险负例不能为了“Fast Mode”被省略。

性能绝对值、AI 样本量及可访问性完整目标暂为待决事项。可以先按上节进行 calibration，但正式 Acceptance 前必须记录并接受测量方法、阈值、任务/样本和停止条件；不事后改阈值掩盖失败。环境不支持 WebMCP 或没有模型预算时，可报告部分进度，但不能判完整 M1 PASS。
