# ADR-0001 · 基础边界

日期：2026-10-03。
状态：**Proposed engineering record**。用户已确认本轮产品方向；本 ADR 的工程表述与具体实现尚待 Review/接受。记录不等于 G0 启动授权。

## 背景

目标同时包含跨框架无样式组件、可访问性、Agent 接入、AI 优先开发与插件化。如果将这些能力塞进组件内部，容易形成 UI 与协议强耦合、重复业务逻辑和多份不一致状态。

## 方向性决策

1. 两个独立子系统：UI 与能力；可选 Binding 连接。
2. 三类核心契约：组件、业务能力、Binding；插件元数据与生命周期作为横向契约。
3. Ark UI 可作为首个 provider，但公共契约由 future-ui 定义；WebMCP 是可替换 adapter。
4. 人与 Agent 复用应用业务动作，授权与实际 effect 由业务执行层落实。
5. AI 开发工具与网站运行时隔离；机器可读、明确诊断与局部修改优先于语法花样。
6. 安装/启动可插拔优先，全面运行时热替换延期。
7. GitHub 是工程事实源；Notion 仅作协作参考，不维护第二套动态事实。
8. 当前仅准备；文档接受、文档 merge、开始开发三个动作分别记录，后两者不能互相推断。

## 未采纳路线

- Ark UI API 简单改名：难以证明独立契约与 provider 替换。
- 每个 DOM/组件事件自动变成工具：混淆局部交互与业务能力。
- 一开始全部 JSON 化或统一所有框架源码：范围过大，先验证共享语义。
- 一开始造全套 Agent/模型/工作流平台：超出 UI 与能力供给边界。
- 复制 webskill 自动 Supervisor：当前只需人工逐步准备与轻量审阅。

## 代价和风险

契约需要额外维护与跨 provider 测试；可访问性需对实际组合验证；协议表达能力可能不足；AI 工具链价值需要对照实验。过度抽象会增加开发成本，首轮用最小纵向示例验证，不凭架构图扩大实现。

## 待决而非默认接受

React/Vue 的精确版本、首批组件、Schema 技术、具体包拆分、WebMCP API/浏览器版本、主题机制、性能阈值和 AI 实验预算均见 [决策登记](../management/decision-register.md)。不得把候选方案标为已验证支持。
