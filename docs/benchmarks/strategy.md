# 验收策略 · UI 语义适配与跨工程一致性

日期：2026-10-05。方向基于负责人最新确认；具体用例/环境在目标 Issue 执行前确定。本文调整未来产品验收主线，不回写 CAL-001 的冻结协议、样本或结论。

## 1. 首先验证的价值

future-ui 适配现有 UI 库，让 AI 沿用统一的组件语义与项目规范，并输出机器可读结构。当前主要问题不是模型能否完成复杂任务，而是通用 UI 约定是否可靠复用。

因此不要求先证明模型优效，也不现在冻结 5%/10% 不劣界值。核心功能正确仍是底线；一致性、明确限制和可用结构是新增产品验收重点。

## 2. 验收矩阵

| ID | 性质 | 最小证据 | 不能替代 |

## 3. 一致性验证方法

选择真实工程的同类编辑弹窗；先冻结共享 Profile 与例外，再完成页面。检查标题、关闭入口、操作角色、pending、token/variant 的对应规则。加入缺关闭入口、版本不符、显式 blocking 例外等正反例。

检查作用于受支持声明/实例/渲染。对没有接入或不支持静态推导的页面报告 not covered；不承诺任意源代码的全站证明。跨库分别报告语义一致、交互一致和视觉差异。

人工纠正次数、规则遗漏、适配成本、版本漂移可观察；没有原始数据就不写“降低了多少”。不通过削弱 baseline、强制工具调用或选择性展示来制造优势。

## 4. 三层正确性与证据等级

结构正确不等于交互正确；交互正确不等于业务权限/效果正确。Schema-valid、metadata、确定性本地组件测试、真实浏览器、真实模型、真实外部写分别记账。请求已发送、取消和超时均不等于业务完成或回滚。

报告包含代码/Profile/Adapter/upstream 标识、用例、环境、实际命令、结果和未测项。一般改动只做最小充分检查；高风险边界和阶段项按需要独立验证。
