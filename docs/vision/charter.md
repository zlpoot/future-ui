# 产品章程 · v0.1 讨论整理稿

日期：2026-10-03。方向来源：本轮用户讨论与确认。状态：方向已确认；本文作为工程基线待 Review，不构成开发启动或具体 API 冻结。

## 定位

future-ui 是 AI 优先开发、契约驱动的模块化 Web UI 框架。重点解决三类不同需求：网站使用者需要可靠可访问的交互；开发 AI 需要明确组件、约束和修复反馈；操作网站的 Agent 需要可发现、可验证、受控的业务能力。

这三种友好性协作但不混成一个模块。项目不是 Ark UI 重命名，也不是把每个按钮直接包装成 WebMCP 工具。

## 原始要求与解释

| 用户要求 | 产品原则 | 对应后续任务 |
| --- | --- | --- |
| 类似 Ark UI，跨框架、无样式、可访问 | 公共组件契约独立于 provider；统一行为语义，不要求所有页面源码跨框架原样运行 | #2、#8、#11 |
| 集成 WebMCP 等 Agent 能力 | 业务能力契约独立，外部协议只通过 adapter 接入 | #2、#9、#12 |
| 便于 AI 开发，可不优先适配人工开发 | 优先确定性、机器目录、结构化校验、局部修改与测试闭环；保留可审查代码与人的可访问性 | #6、#13 |
| UI 与 Agent 接入可插拔、解耦 | 两个独立子系统，加可选 Binding；允许任一子系统完全不存在 | #7、#9、#10、#14 |

## 价值假设

在相同模型、任务和预算下，明确契约与开发工具链有望减少错误 API、无效组合、整页重写和修复成本。这是待实验验证的假设，不是已取得的效果。

AI 开发过程应形成：发现正确组件 → 生成合法结构 → 获得准确诊断 → 局部修复 → 验证真实交互。运行期 Agent 接入则形成：发现能力 → 校验权限与前置条件 → 调用共享业务动作 → 返回真实结果并更新界面。

## 必须成立的四种使用模式

1. UI-only：组件与主题无需能力模块、协议客户端或模型 SDK。
2. Agent-only：旧页面不换 UI，也能接入能力契约和受控调用。
3. 组合模式：UI 与 Agent 复用业务动作，通过 Binding 映射必要状态。
4. 替换模式：在声明的共同契约范围内替换 provider、主题或协议；特性不兼容时明确失败。

## 首轮验证范围（候选，不是已实现）

纵向示例：商品选择 → 修改数量 → 加入购物车 → 展示真实执行结果。仅受控本地示例，不含真实支付。

React 主实现、Vue 小范围对照；Ark UI 首个 provider；至少一个组件提供不同 provider 以验证替换。一组基础表单组件与 Dialog、一套可选主题、独立能力模块、可选 Binding、WebMCP 实验适配器，以及最小 AI 开发工具链。精确组件、版本、API、浏览器和预算在 #2/#3 冻结。

## 非目标

首轮不做完整 Agent 推理循环、模型管理、跨站工作流、后端业务平台、插件市场、不可信远程插件执行、全部组件/框架适配、任意 UI 的新编程语言、所有行为的运行时热替换、生产化身份基础设施、真实支付、部署或 npm 发布。

这些范围不能由“未来需要”自动扩展。需要时另立 Issue 与决策，不为其填充空包或假实现。

## 与 webskill 的关系

future-ui 偏能力供给侧：帮助开发者/AI 建立界面并显式提供操作能力。webskill 偏能力接入、学习、组合和执行侧。未来可以通过公共契约或 adapter 协作，但双方不得互为强制依赖；本项目不修改 webskill 仓库。

## 成功标准

成功不是组件数量、文档数量或测试数量，而是四种模式和核心交互/安全边界在规定环境得到证据，并通过 AI 对照验证是否带来实际开发收益。未测、失败、部分支持与延期必须分别报告。具体矩阵见 [验收策略](../benchmarks/strategy.md)。
